모니터링¶

운영 모드¶

공통 설정은 현재 active입니다. 수집·대시보드·Prometheus 규칙 평가를 유지하며 명시적으로 분류된 operational alert를 Slack bridge로 전송하고 Watchdog은 healthchecks.io로 직접 보냅니다. 미분류 알림은 discard 처리합니다. observe는 수집·평가를 유지하면서 외부 전송을 중단하고, paused는 수집·평가도 중단합니다. 모드 전환과 실제 알림·복구 전송 테스트는 별도 승인 대상입니다.

active에서는 즉시 대응과 업무시간 대응을 구분합니다. 업무시간은 평일 09:00–18:00 Asia/Seoul이며 공휴일 예외나 요약 발송은 없습니다. 아래 알림 연결도는 활성 모드의 경로입니다. 설정만으로 전달 성공을 판정하지 않고 실제 수신을 확인합니다.

보수 중 자동 업데이트 차단¶

자동 업데이트 차단 여부는 각 호스트에서 systemctl cat auto-upgrade.service auto-upgrade.timer auto-reboot.service auto-reboot.timer로 확인합니다. 런타임 drop-in의 존재를 Git 선언만으로 추정하지 않습니다.

/etc/systemd/system.control/{auto-upgrade,auto-reboot}.{service,timer}.d/90-migration-pause.conf가 있으면 재부팅과 일반 Nix 배포 후에도 차단될 수 있습니다. /run/systemd/system/의 동일 이름 drop-in도 확인합니다. /run/infra-maintenance-resume-automatic-updates marker 생성으로 실행 조건을 우회하지 않습니다.

차단 해제는 변경 검토·배포·운영 검증을 마친 뒤 별도 승인으로 수행합니다. 해당 drop-in을 제거하고 daemon reload·timer 재활성화 후 다음 실행 시각과 실제 적용 상태를 확인합니다.

  • SjangLab Access & Audit: 맨 위 침해 징후(평소 0)·로그인 출처·공격 압력, 아래 접힌 SSH/tailnet/Authentik/Headscale drilldown
  • SjangLab Public Edge: eta 공개 vhost 트래픽, 스캐너 경로, 큰 요청 본문, 5xx, 민감 경로 응답
  • SjangLab Hosts: 호스트 리소스, 데이터 파일시스템, SMART·NVMe·RAID, auto-upgrade 결과, Headscale 노드 상태
  • SjangLab Apps: Gatus 내부 체크와 Blackbox 외부 probe 비교, Nextcloud PHP-FPM·5xx·경고 로그
  • SjangLab Jobs: Borg 백업·무결성 검사와 PostgreSQL 덤프의 마지막 완료 기록
  • SjangLab AI Resources: AI 서비스 smoke, psi 리소스, 데이터 동기화 상태
  • SjangLab PostgreSQL: rho primary, tau replica, streaming lag, slot WAL 여유, replication 감사 이력
  • Gatus: https://status.sjanglab.org (eta 공개 HTTPS + Authentik 구성원 인증 상태 페이지)
  • PostgreSQL은 primary rho와 replica tau를 별도 endpoint로 표시합니다.

Grafana 사용 순서¶

  1. Grafana에 접속해 Authentik으로 로그인합니다. 공개 HTTPS 경로는 VPN이 필요 없으며 기존 sjanglab-admins 인가 정책을 유지합니다. 신규 사용자는 Viewer이며 공유 관리자 계정이나 별도 API 토큰이 필요하지 않습니다. 접근 거부는 Authentik 인가·그룹을 확인하고, 헤더 위조나 인증 우회로 해결하지 않습니다.
  2. 우측 상단 시간 범위를 평소에는 최근 6시간, 야간 작업 점검에는 최근 24시간으로 선택합니다. 패널이 비어 있으면 기간을 늘리고 수집 상태부터 확인합니다. No data를 성공이나 0건으로 해석하지 않습니다.
  3. Hosts에서 Metrics freshness, Prometheus targets, 디스크·CPU·메모리를 먼저 봅니다. 수집 경로가 끊긴 상태에서 다른 패널의 과거 값을 현재 상태로 판정하지 않습니다.
  4. Jobs에서 Latest recorded outcome과 Last completion time을 함께 봅니다. Success만으로 예약 실행·무결성·복원을 판정하지 않습니다.
  5. 앱 장애는 Apps, DB 복제는 PostgreSQL, 로그인·권한 문제는 Access & Audit에서 같은 시간대를 확인합니다.

공개 경로는 eta nginx → rho nginx → localhost Grafana입니다. eta는 rho 인증서의 CA·hostname을 검증하고 외부에서 받은 identity 헤더를 버립니다. 교차 서명된 중간 CA 체인을 허용하도록 TLS 검증 깊이는 4로 설정합니다. 502가 발생하면 실제 upstream 인증서 체인을 확인하며 인증서 검증을 끄지 않습니다. rho가 Authentik 인가 후 identity를 다시 설정하며, 클라이언트 주소 헤더도 eta peer에서 온 경우에만 신뢰합니다. 익명 접근은 끄고 신규 Grafana 계정 기본 역할은 Viewer로 유지합니다. Viewer도 데이터소스 조회가 가능하므로 SSO 접근 그룹을 확대할 때 로그 열람 범위를 함께 검토합니다.

Headscale split DNS는 내부 rho 경로를 유지합니다. /prometheus/와 /alertmanager/는 공개 eta 경로에서 404이며, 내부 경로 또는 SSH 터널을 사용합니다. Grafana의 자체 /api/·WebSocket은 인증 뒤에 제공하며 직접 Prometheus/Loki API를 공개하는 설정이 아닙니다.

공개 경로 변경은 terraform/dns의 logging.sjanglab.org 레코드와 eta·rho 설정을 함께 적용해야 합니다. rho의 인증·헤더 신뢰 설정을 먼저 적용하고, eta의 public ACME 발급·rho 인증서 동기화를 확인한 뒤 공개 접속을 검증합니다. 선언 추가나 기존 인증서 파일만으로 적용 완료를 판정하지 않습니다. 검증 기준은 VPN 없는 접속의 로그인 유도, 승인 사용자 dashboard·Live 연결, identity 헤더 위조 거부, public 관리 경로 404, 내부 관리 경로 유지입니다. public DNS를 추가해 HTTP-01 발급을 시작하기 전에는 기존 DNS-01 인증서를 제거하지 않습니다.

인증서 동기화에서 failed to set times가 발생하면 rho의 수신 디렉토리와 파일·심볼릭 링크 자체의 소유권을 수신 계정 acme-sync-logging과 비교합니다. 링크 소유권 수정에는 chown -h를 사용해 대상을 따라가지 않으며, 개인키·인증서 본문을 로그에 출력하지 않습니다. 동기화 서비스 정상 종료와 nginx reload까지 확인합니다.

Access & Audit 패널 판독¶

SSH Access audit와 Tailnet app access는 원본 SSH·nginx 로그가 아니라 rho의 두 correlator가 가공한 기록입니다. observe에서도 수집하며 timer 활성화 60초 뒤 첫 실행, 이후 60초 간격으로 실행합니다. active (elapsed)이면서 다음 실행이 없으면 정상 수집 상태가 아닙니다. 다음 trigger, 최근 서비스 완료, correlator_heartbeat와 원본 로그를 함께 확인합니다. 수집 재개만으로 과거 공백이 자동 복구되지는 않습니다. 공개 Grafana 요청은 tailnet audit 대상이 아니며 원본 nginx_access에서 확인합니다.

Jobs 패널 판독¶

표시 의미 추가 확인
Success 마지막으로 기록한 실행이 정상 종료 완료 시각이 충분히 최근인지 확인
Unsuccessful 마지막 완료가 비정상 종료 같은 실행의 systemd 결과·원인 확인
No completion data / 행 없음 완료 관측 없음 미실행과 수집 누락 구분
scheduled=true 선언에 일정 있음 실제 timer 활성화·다음 시각·마지막 trigger는 systemd 확인
결과 시계열의 연속 0 마지막 성공 값이 반복 수집됨 성공 실행 횟수나 매분 백업을 뜻하지 않음

Jobs는 psi·rho·tau의 Borg와 PostgreSQL 덤프만 표시합니다. eta Restic·Stalwart 작업은 이 패널에 없으므로 전체 백업 상태판으로 사용하지 않습니다. eta는 systemd timer/service와 Loki의 backup snapshot을 별도로 확인합니다. Explore 권한이 있는 사용자는 Loki에서 다음 쿼리로 작업별 unit, health, health_reason을 확인할 수 있습니다. Explore가 보이지 않으면 권한을 요청하며 익명 접근을 열지 않습니다.

{host="eta", log_type="systemd_status", event="job_snapshot"} | json | job_class="backup"

로그 자체가 없으면 정상이라는 뜻이 아닙니다. 서비스가 inactive (dead)여도 oneshot은 정상 종료 후 그렇게 표시됩니다. Result, ExecMainStatus, 시작·종료 시각을 같은 실행 기준으로 함께 봅니다. 예약 성공을 확인하려면 timer의 LastTriggerUSec가 서비스 시작 시각과 연결되고, 그 실행이 정상 종료했는지 확인합니다. 수동 실행 성공만으로 자동 예약 검증을 완료하지 않습니다.

Grafana는 관측 화면이며 백업 실행기나 알림 전송 확인서가 아닙니다. observe에서도 같은 대시보드를 사용합니다. active 승인은 실제 firing/resolved 수신과 독립 Watchdog 전달을 확인하는 절차와 분리하지 않습니다.

eta는 SSH 인증 로그와 같은 PID의 outbound socket을 관찰해 ssh_bastion 로그를 생성하고 Loki로 직접 전송합니다. ProxyJump 때문에 대상 호스트가 eta의 내부 IP만 보더라도 실제 접속원 IP, bastion 사용자, 대상 호스트를 함께 조회할 수 있습니다.

{log_type="ssh_bastion", event="bastion_forward"}

대상 호스트의 SSH 로그와 맞출 때는 target_host, bastion_user, 시간대, bastion_local_port를 함께 봅니다. 대상 호스트 sshd 로그의 source_port가 eta에서 기록한 bastion_local_port입니다.

백업 완료 결과¶

psi·rho·tau의 Borg·PostgreSQL 덤프는 종료 시각과 정상 완료 여부만 기록합니다. Vector가 infra_job_last_completion_timestamp_seconds와 infra_job_last_result를 전송하며, 최초 완료 전에는 값을 생성하지 않습니다. 결과 0은 정상 완료, 1은 비정상 완료입니다. 실행 중 상태나 별도로 보존된 마지막 성공 이력으로 해석하지 않습니다.

Jobs 대시보드는 마지막 완료 결과와 경과 시간을 표시합니다. 예약 백업·주간 Borg 무결성 검사의 실패, 선행 덤프 실패, 백업 36시간·검사 9일 완료 지연, 완료 관측 누락을 구분합니다. 주간 검사는 파일 추출이나 DB 복원을 하지 않습니다. 누락은 실패나 복구의 증거가 아닙니다. 일정·범위·복원 절차는 백업 문서를 봅니다.

접근 감사 (Authentik / Headscale)¶

eta의 Vector가 journald에서 수집해 이벤트를 분류합니다 (modules/authentik/audit.nix, modules/headscale/audit.nix):

  • Authentik (log_type="authentik"): login, login_failed, logout, app_authorize(브라우저 앱 인가), admin_change, policy_error, forward_auth_deny
  • Headscale (log_type="headscale"): node_register, node_expire, preauth_key, oidc_denied, error — 컨트롤플레인/멤버십 감사이며 tailnet 데이터플레인 트래픽은 관측 대상이 아닙니다
  • Headscale 노드 인벤토리 (log_type="headscale_nodes"): 5분 주기 스냅샷 (event="node_snapshot")과 집계 행(event="nodes_summary")으로 node, user, IP, tags, online, health, health_reason, last_seen_seconds, expiry_seconds를 기록합니다
{log_type="authentik", event="login_failed"}
{log_type="headscale", event="node_register"}

레이블 정책: Loki 레이블은 bounded 값(host, log_type, event)만 사용합니다. user, source_ip, app, node 등 고카디널리티 값은 JSON 필드로만 저장하고 LogQL | json으로 조회합니다. 시크릿/쿠키/인증 헤더는 수집하지 않습니다. Authentik login/app_authorize 이벤트의 client_ip는 실제 클라이언트 IP로 보존하지만, forward_auth_deny의 remote는 내부 프록시 주소일 수 있어 proxy_remote 필드로만 기록합니다.

Prometheus (rho)¶

  • 리텐션: 30일
  • Remote write receiver 활성화
  • Scrape jobs:
  • vector: rho Vector exporter
  • blackbox_exporter: eta blackbox exporter 자체 health
  • alertmanager: rho Alertmanager health (Alertmanager SOPS keys가 있을 때)
  • blackbox_http: eta vantage public HTTPS probes (auth, hs, n8n)
  • blackbox_tailnet_http: eta vantage wg-admin HTTPS probes with Host/SNI override for tailnet-only apps (n8n-ui, nextcloud, etc.). Grafana는 공개 HTTPS/login 경로를 검사하며 인증 후 dashboard 내용까지 검증하지는 않습니다.
  • blackbox_tcp: eta vantage TCP probe for Upterm
  • blackbox_icmp: eta vantage ICMP probe for wg-admin host reachability
  • nvidia-gpu: psi GPU exporter
  • postgresql: rho/tau local postgres_exporter metrics relayed through Vector
  • Alert rules: 호스트 관측 누락, 공간 부족, PostgreSQL 상태·replication, 등록 서비스 probe 실패·관측 누락, TLS 만료, Vector 전송 오류, 규칙 평가 실패, 예약 작업·백업 덤프 실패·완료 지연·관측 누락, RAID·SMART 상태와 수집 누락, Watchdog
  • Alert delivery: 현재 active에서 정책상 대응이 필요한 operational alert를 Cloudflare Worker/D1 bridge로 전송합니다. observe로 되돌리면 외부 전송을 discard 처리합니다. 서비스별 소유 호스트·접근 경로·대응 정책은 modules/monitoring/targets.nix에 선언하며, 의존 대상 장애는 종속 경보를 억제합니다.
  • Alert bridge: Bridge는 자체 healthchecks.io heartbeat를 사용합니다. healthchecks.io 알림은 별도 cutover 전까지 기존 Slack integration을 유지합니다.

Alert response runbook¶

공통 절차:

  1. Slack alert의 host, service, alert_category, dashboard_url, runbook_url를 확인합니다.
  2. Grafana dashboard에서 같은 시간대의 metrics/logs를 확인합니다.
  3. 서비스 단위 장애면 systemctl status <unit>와 journalctl -u <unit> -e를 먼저 확인합니다.
  4. 사용자 영향이 있으면 #infra-alerts에 조사 시작/완료 시간을 남깁니다.
  5. 원인을 모르면 silence하지 않습니다. 노이즈성 반복일 때만 만료 시간이 있는 silence를 설정합니다.

alert별 1차 확인:

Alert 1차 확인 다음 조치

Watchdog 미수신 Alertmanager, healthchecks.io ping URL, 네트워크 Alertmanager 복구. bridge 장애와 분리 확인

알림 판정은 Prometheus만 합니다. Loki는 원인 조사와 감사 조회용이며, 로그에서 나온 신호는 Vector log_to_metric으로 숫자로 바꾼 뒤 Prometheus 규칙이 판정합니다. 보안 알림(SshLoginUnclassified, SensitivePathServed, HeadscaleNodeAdded)도 #infra-alerts로 갑니다. 사용자명, source IP, app/node 정보를 기록하고 계정 탈취 가능성이 있으면 Authentik 계정 비활성화와 Headscale ACL apply를 우선합니다. 공격 압력(스캔, 차단, forward-auth 거부)은 알림 없이 Security & audit 대시보드에서 추세로 봅니다.

#infra-audit에는 rho의 infra-audit-digest.timer가 매주 금요일 15:30 KST에 주간 감사 요약을 게시합니다. 침해 징후 4개(평소 0), 새 tailnet 노드, SSH 로그인 출처, 공격 압력(fail2ban, 인증 전 거부, forward-auth 거부, 스캐너 출처와 404 범주)을 담고, 0건이어도 게시합니다. 요약이 오지 않으면 파이프라인 고장입니다. 쿼리가 실패하면 요약에 실패 항목을 표시하고 서비스가 실패로 끝나 ScheduledJobFailed가 #infra-alerts로 갑니다. 수동 실행은 systemctl start infra-audit-digest, 게시 없이 확인은 rho에서 digest.py --dry-run입니다.

PostgreSQL replica recovery¶

일시적인 네트워크 장애는 slot이 보존한 WAL로 자동 복구됩니다. requested WAL segment ... has already been removed 또는 wal_status=lost이면 기존 PGDATA를 다시 시작하지 않습니다.

  1. tau의 postgresql.target을 중지합니다.
  2. /var/lib/postgresql/17을 timestamp가 붙은 17.stale-* 경로로 이동해 보존합니다.
  3. rho의 inactive/lost tau slot을 삭제하고 physical slot을 다시 만듭니다.
  4. inv deploy --hosts tau를 실행하면 postgresql-replica-init이 pg_basebackup --slot=tau로 새 replica를 구성합니다.
  5. rho pg_stat_replication의 application_name=tau, state=streaming과 tau pg_is_in_recovery()=true를 확인합니다.
  6. Grafana와 Loki에서 byte lag 0, healthy audit snapshot, replica_basebackup_completed를 확인합니다.

stale PGDATA는 새 replica와 backup 검증 완료 전 삭제하지 않습니다.

Alert delivery bootstrap¶

Slack 앱 설정은 slack/infra-alerts/slack-app-manifest.json이 source of truth입니다. slack/infra-alerts 디렉터리에서 direnv를 허용하면 Slack CLI가 포함된 slack-deploy shell에 들어갑니다:

cd slack/infra-alerts
direnv allow

운영 원칙:

  • Slack app/bot/scope: manifest JSON으로 선언하고 Slack CLI가 .slack/hooks.json을 통해 app을 생성/업데이트합니다.
  • Slack app install: Slack CLI로 app을 install하고, 필요하면 admin OAuth 승인을 완료합니다.
  • Slack channel: workspace resource라 수동으로 준비합니다 (#infra-alerts, #infra-audit).
  • Slack bot token: external alert bridge가 chat:write로 메시지를 생성/수정할 때 사용합니다. CI에 넣지 않습니다.
  • Slack webhook URL: bridge migration 동안만 유지되는 channel-bound secret입니다.
  • healthchecks.io checks: terraform/healthchecksio에서 rho-alertmanager-watchdog와 infra-alert-bridge-heartbeat를 관리하고, sensitive ping_url output을 SOPS에 수동 저장합니다. healthchecks.io Slack integration은 bridge migration 동안 유지합니다.
  • Alert bridge: terraform/alert-bridge가 Cloudflare Worker/D1/secret binding/cron을 관리합니다. D1 migration은 Worker 배포 후 수동으로 실행합니다.
  • CI: manifest JSON syntax 검증만 합니다. Slack token이나 webhook URL을 CI에 넣지 않습니다.

필요한 SOPS keys:

alertmanager-bridge-token: ENC[...]
alertmanager-healthchecks-ping-url: ENC[...]

Rollback window 동안만 legacy Slack incoming webhook secrets를 유지합니다:

alertmanager-slack-infra-alerts-webhook: ENC[...]
alertmanager-slack-infra-audit-webhook: ENC[...]

자세한 Slack bootstrap/drift check 절차는 slack/infra-alerts/README.md를 봅니다.

Alert bridge cutover¶

active 모드의 Alertmanager 전송 경로는 Cloudflare Worker bridge입니다. 새 활성화나 재활성화에서는 별도 승인 후 아래 절차를 수행합니다. 실제 Slack firing/resolved 수신과 healthchecks.io의 독립 Watchdog 수신을 확인하지 못하면 observe로 되돌립니다.

  1. terraform/alert-bridge apply 완료 확인
  2. packages/infra-alert-bridge에서 D1 migration 실행
  3. Worker GET /healthz와 cron heartbeat 확인
  4. Alertmanager receiver가 bridge POST /alertmanager와 bearer token을 사용하는지 확인
  5. 실제 선언된 receiver의 대상인 #infra-alerts에서 firing/resolved/update 메시지가 같은 thread로 정상 생성되는지 확인. bridge의 #infra-audit 지원만으로 감사 채널 전송을 가정하지 않으며, 전용 receiver 추가 시 별도 검증
  6. rollback window 동안 legacy Slack webhook secret 유지
  7. 안정화 후 incoming-webhook Slack scope와 webhook SOPS key 제거

healthchecks.io webhook integration은 아직 legacy Slack integration을 유지합니다. 이후 bridge POST /healthchecks와 bearer token으로 전환합니다. Worker 장애가 Watchdog ping 자체를 막지 않도록 rho-alertmanager-watchdog은 healthchecks.io로 직접 ping합니다.

Loki (rho)¶

  • 리텐션: 기본 7일, 감사·원본 접근·Nextcloud 스트림(log_type=~"ssh|ssh_bastion|access_audit|audit|authentik|headscale|postgresql_audit|nginx_access|nextcloud")은 90일
  • headscale_nodes 스냅샷은 반복 상태 데이터라 기본 7일 적용
  • 스토리지: 로컬 파일시스템 (/var/lib/loki)

Gatus (eta)¶

  • Pull 방식: eta에서 직접 접근 가능한 서비스 (Authentik, Headscale, Upterm 등)
  • Push 방식: 내부 서비스가 로컬/사용자 경로를 확인한 뒤 상태 보고
  • 접근: eta 공개 vhost에서 Authentik Forward Auth로 보호. tailnet 장애 중에도 열람 가능. push API(/api/v1/endpoints/*/external)는 공개 경로에서 404이고 wg-admin :8081로만 받음
  • 저장소: SQLite (/var/lib/gatus/gatus.sqlite)로 재시작 후 uptime 유지
  • External endpoint heartbeat: 15분 동안 push가 없으면 실패 처리
  • 그룹: apps, ai, ci, monitoring, platform, storage
  • 기본 정렬: group 기준
  • 알림: Gatus 직접 전송 없음. observe에서는 외부 알림을 보내지 않습니다. 서비스 경보는 등록된 probe와 대응 정책을 기준으로 평가합니다.
